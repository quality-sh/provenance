# Pull request 205, second fix: the close lock could deadlock and did not
# survive cancellation

The close-order change at `ad3098a9d05177487792d9504b10cd2746a96371` closed
the original defect: two reads finishing at the same moment left a
`provenance.db-wal` file behind. Verification of that head found two new
majors, both reproduced here before any change was made, and both fixed in
commit `7f4e924fa2e10bbb978c46baa882e5462f64d90a` on
`1wh-w5-release-mechanics`.

## Reproducing the two majors

Both reproductions ran against an unmodified copy of `ad3098a` with the
reviewer's test-only probe modules added, built in a separate target
directory with `CARGO_BUILD_JOBS=3` in the foreground. The probe points,
`run_migrations_under_guard` and the SQLx progress-handler pause, are test
hooks only; production code was untouched in the probe copy.

### The blocking-pool wait could deadlock a valid operation

With one blocking worker occupied by a competing publication call, and with
four workers occupied by four such calls, the closing read waited for a
worker that waited for the publication guard the read itself held:

```text
blocking_workers=1 read_timed_out=true
cycle=read_holds_publication_lock/worker_waits_publication_lock/read_close_waits_worker
blocking_workers=4 materialization_timed_out=true fault_injected=false
```

The same two probes finish on main, which confirms the cycle came from the
close lock's `spawn_blocking` wait and not from older synchronous work.

### Cancellation and a panic released the lock before teardown finished

With the physical close of the first pool paused inside its progress-handler
destructor, aborting the reader and panicking it both freed the close lock
while that teardown was still paused, and a second close then passed it:

```text
panic=false first_physical_close_paused=true close_lock_released=true
panic=false second_close_finished_while_first_physical_close_paused=true
panic=true  first_physical_close_paused=true close_lock_released=true
panic=true  second_close_finished_while_first_physical_close_paused=true
```

## The design

The two faults share one cause: the reader's own future owned both the wait
for the close lock and the close itself. Ordering closes through a lock
taken on the blocking pool is what created the deadlock, and owning the lock
in that future is what let cancellation and a panic drop it early. The fix
moves both concerns into a detached close task and changes how the lock is
waited for:

- `close_cache` spawns `close_in_order` with a clone of the pool handle and
  awaits it. The close task opens `provenance.db.close.lock`, retries a
  non-blocking `flock` every 1 ms until it holds the lock, closes the pool
  until it holds no connection, and only then drops the lock file.
- The wait needs no blocking worker. A non-blocking attempt returns at once,
  so publication waiters can occupy every blocking worker while the closing
  read holds the publication guard and the close still proceeds. This is the
  property the old `spawn_blocking` wait could not have.
- The lock outlives the reader. A read cancelled mid-close drops only its
  join handle; a read that panics there does not touch the close task. In
  both cases the close task keeps the lock, finishes the teardown, and
  releases the lock afterwards, so the order the original fix relies on
  holds in both cases.
- The lock is released only after the pool reports no connections. A pool
  with no connection has dropped every connection state, which is the moment
  the last SQLite handle is gone, so the lock covers the whole physical
  teardown.
- A lock that cannot be acquired is still reported after the pool closes,
  as before, and immutable reads still use neither the -wal and -shm files
  nor a lock file.

Retry-based cleanup without a lock was considered and rejected: it makes the
guarantee probabilistic, while the ordered lock keeps the guarantee exact.
Waiting on the lock through the blocking pool with a deadline was rejected
because a blocked close that times out degrades to unordered closes, which
is the original defect.

## The three sets of numbers

All builds and runs were foreground commands with `CARGO_BUILD_JOBS=3`,
`df -h /` checked before each build, and `target/` deleted afterwards.

### The original defect stays closed

Release-build store test binary, one fresh process per repetition, both
unchanged concurrent tests per process unless stated:

```text
ordinary: FINAL iterations=1000 tests=2000 failures=0 elapsed=202.6s loaded=False
loaded:   FINAL iterations=1000 tests=2000 failures=0 elapsed=273.7s loaded=True
eight:    FINAL iterations=1000 tests=1000 failures=0 elapsed=115.6s loaded=True
```

The loaded runs pinned the test processes and four busy loops to CPUs 0-3.
The eight-reader run used the new
`eight_answers_that_close_together_remove_the_wal_files`, which opens eight
snapshots at one barrier, checks every count, serial, and freshness result,
and requires both the -wal and -shm files to be gone afterwards.

### The blocking-pool probes finish on a small worker pool

The reviewer's probes, run against the fixed source with the same one and
four worker settings:

```text
blocking_workers=1 read_timed_out=false
read_finished_without_timeout result=Err(no projection revision ... catch-up
failed: verification: the freshness step fails while another publication waits)
blocking_workers=4 materialization_timed_out=false fault_injected=false
materialization_finished result=Ok(MaterializeReport { records_loaded: 0, ... })
```

The four permanent tests in
`cache/tests/close_order_behavior.rs` guard the same schedules; each of the
four fails on the previous close (deadlock timeouts for the two
blocked-worker tests, early lock release for the cancelled and panicking
reader) and 100 repetitions of the four, 400 executions, gave zero failures.

### Cancellation and panic leave no -wal or -shm file behind

The reviewer's probes now report the opposite of the defect and fail at
their own assertion that the gap exists:

```text
panic=false first_physical_close_paused=true close_lock_released=false
probe expects the current cancellation gap
panic=true  first_physical_close_paused=true close_lock_released=false
probe expects the current cancellation gap
```

The two permanent tests keep the same schedules and assert the fixed
behaviour: the lock stays held after the reader is gone, no later close
passes the paused one, the lock frees once the teardown resumes, and the
-wal and -shm files are gone at the end. A single-threaded run of the probe
copy of the fixed tree against every store test shows the same picture: 407
passed with only the two gap-assertion probes failing.

For scale, the full store unit suite on the fixed tree passed 401 tests with
one ignored in a release build with three test threads, and the workspace
all-feature suite and the default-feature CLI suite passed with zero
failures.

## Deliberately left alone

- An unwind raised inside the close task itself, rather than in the reader,
  would still drop the lock during unwinding. Nothing in the reader path can
  panic there: reader code never runs inside the close task, and SQLx close
  has no panic path in use. Runtime shutdown with a detached close still
  pending releases the lock at drop, which matches the pre-branch behaviour
  of a process exit during teardown. Catching panics inside the close task
  would need an unwind wrapper the crate has no dependency for, to guard a
  case no reader can reach, so it was left out and the boundary is stated
  here instead.
- The 1 ms retry interval is a fixed constant, not a tunable setting. Lock
  hand-off under eight readers stays in the millisecond range and the poll
  never needs a worker.
- The lock file stays in place between closes, immutable reads still create
  no lock file, and `close_cache` keeps its signature and call sites, so the
  read-only mount behaviour verified at `ad3098a` is untouched.
- The two original concurrent tests are unchanged; the eight-reader test was
  added beside them rather than replacing them.
- The deferred work named in the earlier review, the stale-refusal change
  and the eight-operation timing report, is untouched, as is branch
  `1wh-w5-refuse-stale`.
