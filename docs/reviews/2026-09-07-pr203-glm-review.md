## Minors

### M1. The lock-free manifest read can observe the publication's rename window as NotFound — the "sees one whole version" claim is slightly stronger than the mechanism

`commit_prepared` (`crates/provenance-cli/src/atomic_file.rs:190-215`) first *displaces* the existing manifest to a backup (`displace_to_backup` → `renameat_with(RENAME_NOREPLACE)`, `atomic_file/commit.rs:4-16`) and only then renames the temp file into place. Between the two renames `manifest.json` does not exist. The plan (G.1: "an unlocked read sees one whole version of it") and the new `docs/cache.md` text ("which is written atomically") promise a bit more than the code delivers: a lock-free `units::scope_ids` reader that hits that window gets NotFound and refuses with `read manifest …: No such file or directory`. The old locking path (`StateStore::manifest` under `with_repository_read`) was mutually exclusive with the manifest writer and could never see this window.

Mitigations, verified: the exposure today is narrow — `ensure_current_schema` consults the scope list only inside the half-migration window (a healthy projection never reads the manifest; see Reproduction R7), the writer runs under the publication lock so the window opens only during repo init / scope publications, and the outcome is a refusal, never a stale answer. K.3's `refuse_stale` will read the scope list on every read and widens the reach of this window to transient refusals of otherwise-servable reads. Consider one NotFound retry, or one sentence in `docs/cache.md` recording the transient refusal.

### M2. The permission tests skip silently when their fixtures cannot bind

`read_only_answer` (`queries/tests/reader/read_only.rs:44-48`) and `a_guard_directory_permission_failure_keeps_its_io_kind` (`:140-144`) return early — reporting *pass* — when a probe write succeeds, i.e. when the 0o555 mode did not stick (running as root). Likewise `cli_sdk_read_only_mount.rs:17-19` returns early when `unshare` is unavailable. A root CI run would therefore count all five permission tests as passed while four of them exercised nothing (the mount test still genuinely runs under `unshare --map-root-user`, since a read-only *mount* blocks root in the namespace too — I verified the mount branch ran here, uid 1000). Suggested: print a skip notice or count skipped tests so a green total cannot overstate coverage. I ran the suite as uid 1000 (non-root), so the results below are the real fixtures.
