## Minors

1. **The lock-free manifest read has a narrow absent-file window.** `units::scope_ids`
   (`cache/materialize/units.rs`) reads `manifest.json` bytes without the lock. The manifest's only
   writer (`handlers/repo.rs` through `atomic_file.rs`) does write to a `create_new` temp file, then
   `sync_all`, then rename — but the rename is preceded by `displace_to_backup`
   (`atomic_file/commit.rs:4-16`), which renames the current `manifest.json` to a
   `.manifest.json.provenance-<pid>-<n>.backup` first. Between that displacement and
   `rename_no_replace(temp, path)` the path does not exist, so an unlocked reader in that window gets
   ENOENT and `ensure_current_schema` refuses the read with "read manifest …: No such file or directory".
   The failure direction is safe — it is a refusal, never a stale answer, and the next read succeeds —
   and the window is microseconds against a write that happens at init/scope-creation time. But the code
   comment ("an unlocked reader sees one complete version of the file") and the matching sentence in
   `docs/cache.md` slightly overstate the guarantee. A one-retry on NotFound, or a sentence acknowledging
   the window, would close the gap. This reasoning is inherited from the plan (section G.1 asserts the
   same atomicity), so the code obeys the plan; the plan's claim is the thing that is marginally too strong.

2. **Vacuous-pass probes in the read-only fixtures.** `read_only_answer`
   (`queries/tests/reader/read_only.rs:44-48`) and `a_guard_directory_permission_failure_keeps_its_io_kind`
   (`:140-144`) return early — passing silently — when a probe write into the `0o555` directory succeeds
   (the case under root), and `a_read_only_mount_answers_without_the_publication_lock` returns early when
   `unshare` is unavailable. Correct on this machine and on Linux CI (verified below), but a skip is
   indistinguishable from a pass in the output. An emitted note (or `eprintln!`) at the skip sites would
   make the evidence honest on hosts where the fixture cannot run.

## Nits

1. `Settings::load` reports root-level problems under the key `$` (for example
   `<path>: $ must be valid JSON: …`). Deliberate (the store test pins `"$"`) and the path is always
   present, but `$` reads cryptically next to the human wording of the other keys.
2. `permission_failure` (`freshness.rs:187-196`) answers the ambiguous SQLite codes 14 and 4618 by
   opening the database file read-write as a probe. The direction is safe — a probe success only means
   the original error is returned (refusal), a probe permission failure only adds the immutable
   fallback — but it is a second unsynchronized open; the existing comment covers it.
3. The two new resolutions (`res_read_settings_live_in_settings_json`,
   `res_freshness_flag_wins_over_settings_file`) bind `req_query_answers_carry_a_freshness_stamp`
   instead of the new requirement they underwrite. They were recorded by the rulings merge (`f126ea8`)
   before the requirement existed, and the coverage scan reports no finding, so this is only a
   cross-link asymmetry, not an error.
4. The repository's own `.provenance/settings.json` pins both keys at their built-in defaults
   (`catch_up`, `5000`). Redundant by construction, but it makes the tracked file exercised and visible,
   which suits the stage's purpose.
5. `handlers/sdk/query.rs` resolves the repository twice (once in the handler for the settings load,
   once inside `served`). This mirrors the pre-existing shape (the handler already called
   `discover_repository` before this PR) and costs nothing observable; noting it only because the
   settings load now depends on the first discovery.

  `queries::*` functions take `policy`, `--freshness` on `QueryArgs` (shared by all eight sdk query

  `units::scope_ids` and `ensure_current_schema` on it, the immutable fallback under `annotate_only` and
  the `catch_up`-failure path, the `lock_untakeable` fixture, `docs/cli.md` replacing the reserved

  and repeat procedure in its doc comment, and the requirement record with its Source. H (`catch_up_failed`
  kept) needed no code, and `docs/cache.md` records the confirmation.
- **Owner rulings obeyed.** Settings in `.provenance/settings.json`, tracked beside `state/` and
  `cache/`, JSON like the manifest; missing file → defaults; invalid value → settings refusal before any
  read, never a freshness outcome, never in `freshness_error`; flag > file > default; no environment
  variable; scan default 5000.
- **`refuse_stale` staging.** The word is accepted by settings, flag, and TypeScript (per E.3's flag
  spec) and refuses as "reserved and not implemented"; no hash-only decision, no `ReadRefusal::Stale`,
  no unlocked-hash step — K.3's work is not pre-empted. `refuse_stale` never produces an answer, so the
  stamp can never name a policy that did not run.
- **Ambiguous-SQLite-code handling.** Unambiguous permission codes (3, 8, 520, 1544) select the
  fallback directly; ambiguous codes (14, 4618) require a confirming read-write open failure with
  `PermissionDenied` or `ReadOnlyFilesystem`; a missing database alone never selects the fallback
  (NotFound is not a permission kind); any other open error is returned as-is (NoProjection / catch-up
  failure with the error text), so the fallback cannot mask a genuinely broken database.
- **`stored()` behaviour change is plan-conformant.** The catch-up-failure path previously fell back to
  the immutable open on *any* open error; it now does so only on permission failures, exactly as section
  I prescribes ("every policy falls back … when the ordinary open fails for a permission reason").
- **Half-migration refusal without the lock.** `a_half_migrated_projection_refuses_without_taking_the_lock`
  deletes `projection_family_digests`, makes the lock untakeable, and gets the typed `HalfMigrated`
  refusal — the schema check really does read the manifest unlocked.
- **Byte identity of the guard refactor.** `canonical_utf8`/`create_real_directory`/`acquire` now use
  context-preserving wraps; mutation-tested both ways (R5); byte identity (above) confirms no served
  byte moved.
- **TypeScript.** `invokeEngine` threads the option only when defined; `info` never receives it; the
  test asserts `stamp.policy == "annotate_only"` with the file pinning `catch_up`, so an ignored option
  would fail it.
- **Docs.** `docs/cli.md` names the file, both keys, the flag words, the precedence, "No environment
  variable selects a policy", the refusal content, and that `refuse_stale` refuses until K.3.
  `docs/cache.md` adds the settings paragraph and the read-only checkout paragraph adapted from the
  plan's suggested text, including the Windows caveat. `CONTEXT.md` gains the two new terms.
- **Working tree hygiene of the review.** All review mutations were reverted (`git status` clean at
  commit time), the battery wrote only gitignored cache, and the temp worktree/target were deleted
