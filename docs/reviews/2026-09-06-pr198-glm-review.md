# PR 198 adversarial review — W5 K.1a, `1wh-w5-readers-under-guard` @ `b77e3d1`

Reviewer: GLM (single adversarial reviewer, stage K.1a of the W5 release-gate plan, revision 3).
Base `main` = `03a935c`. Four commits: `38b9bba` (ideation validation module split), `dfc595d`
(guarded stores read without a second lock), `3aa60c8` (guarded writes keep the publication lock),
`b77e3d1` (guarded stores become read-only). The stage is a zero-behaviour-change refactor:
canonical readers take their lock state from the store they read through; the state-tree copy stays.

## Verdict

**Mergeable as-is.** No behaviour change found: every served byte the plan pins is identical between
`b77e3d1` and `03a935c`, no path can read or write a repository without the lock it needs, and no
path can take a lock twice. The findings below are minors and nits; none blocks the stage. The two
most useful ones for the follow-up stages: the guarded read surface silently dropped five public
reads that exist on `StateStore` (the deadlock fix traded the plan's `Deref` design for an
allow-list and narrowed the capability with it), and one plan-mandated test now tests something the
type system already forbids.

## Majors

None.

## Minors

1. **The guarded read surface omits five public reads of `StateStore`.** `StateStore` has 31 public
   pure-read methods; `GuardedStore` forwards 26. Missing: `plan_typed_spec` (Plan mode writes
   nothing — every write in `reconcile_typed_spec` is gated on `ReconcileMode::Apply`,
   `typed_specs.rs:215`), `list_requirement_reviews` (`requirement_reviews.rs:113`),
   `rule_ids_for_requirement` (`requirement_reviews.rs:130`), `list_verification_runs`
   (`verification_runs.rs:153`), `surface_proposals` (`proposal_surfaces.rs:89`). None has a caller
   today: `StateStore::under_guard` has no production caller at this head (K.1b introduces them),
   and the plan's C.2.2 call-site list (`validate_graph_scope`, `rederive_scope`,
   `relation_rows::scope_rows`, `canonical_artifacts`, `manifest()`, `validate_ideation_scope`) is
   fully covered by the exposed surface — so this is not a plan violation. But the capability claim
   in the rule description ("reads without a second lock") is narrower than the type it replaced:
   under dfc595d's `Deref` design every read was reachable under a guard; after b77e3d1 a served
   process holding a guard cannot read reviews, verification runs, or plan a typed spec without
   falling back to a plain store, i.e. without queueing behind the publication — the exact deadlock
   this stage removes. Note that `list_requirement_reviews` and `list_verification_runs` do not take
   the publication lock at all (the first takes none — pre-existing, see below; the second takes
   only its advisory lock), so exposing them on `GuardedStore` would be trivially safe today.
   Recommendation: either expose the five reads in K.1b, or record in the K.1b/K.2 plan text that a
   guarded caller cannot serve these families.
   Reproduced by inspection: `GuardedStore` impls are exactly `access/guarded_readers.rs:8-134`;
   the five names appear nowhere in it.

2. **`a_cloned_plain_store_still_waits_for_the_lock` no longer tests what the plan named, and now
   pins nothing the compiler does not.** Plan C.3 named `a_cloned_store_locks_again`: a clone taken
   *through the deref of a guarded store* must yield a store that locks again. That scenario is
   unrepresentable after b77e3d1 — `GuardedStore` is not `Clone` and has no `Deref` — and the
   compile-fail cases already pin that. What remains is `store.clone()` on a *plain* store (source
   `Access::Lock`), which executes one extra `impl Clone for StateStore` call and then repeats
   `a_plain_store_still_waits_for_the_lock` verbatim. No reachable `Clone` implementation could make
   this test fail while the sibling test passes: the source store is plain, so any clone is plain.
   Recommendation: delete the test; the hand-written `Clone` (access.rs:19-23) is adequately pinned
   by it being the only `Clone` impl plus `a_plain_store_still_waits_for_the_lock`.

3. **The PR body omits the before test count that the staging plan requires.** Section K of the plan:
   "Each PR body states the test count before and after with the added and deleted tests named."
   The body gives only the after count (1,598 passed, 0 failed, 4 ignored — I reproduced that
   exactly) and names the added/deleted tests narratively, but never states the before count
   (base = 1,593 by the five-test delta of `access/tests.rs`; not re-measured on the base tree).
   Process defect only.

## Nits

1. **`read_message_shards` now records one extra probe read.** Base locked the message read through
   `with_repository_publication(layout, …)` and recorded only the month-shard paths
   (`read_jsonl_shards`); head routes through `state_path_access(&threads_path, …)` (readers.rs:320),
   which additionally records the threads path itself. Production no-op (`test_probes::record_read`
   is a no-op outside tests, `test_probes.rs`), and the recorded path still lies inside the scope's
   directory, so `scope_locality_guard` stays honest — but the recorded-read set that K.1b's
   `catch_up_reads_the_state_tree_in_place` will assert on gains one entry per `list_messages` call
   that base did not have. Worth knowing when K.1b writes that test.

2. **`snapshot_under_guard_takes_no_second_lock` (publication/guard.rs:161) asserts less than its
   name claims.** It now verifies only that the snapshot copied the *guard's* repository (the probe
   file appears) — the `rule_guarded_reads_use_guard_repository` half. It never asserts the
   publication lock is held during the copy, unlike the store-side sibling test. Rename it (e.g.
   `snapshot_under_guard_uses_the_guard_repository`) or add a
   `publication_lock_is_held` assertion so the name is earned.

3. **`a_store_under_the_guard_takes_no_second_lock` couples the unit suite to the repository's own
   working tree** (access/tests.rs:75-81: `snapshot_state` on `CARGO_MANIFEST_DIR/../..`). It takes
   the real repository's publication lock inside `snapshot_state` with no timeout; a concurrent
   `provenance` process on the same checkout blocks the test run indefinitely. Every other guard
   test in the crate builds a tempdir repository. Consider a fixture layout instead.

## Things checked and found fine

- **No unlocked read or write, no double lock.** Every one of the five reader helpers
  (`read_jsonl`, `read_ideation_landings`, `read_legacy_dispositions`, `read_jsonl_closed`,
  `read_message_shards`) now routes through `store.state_path_access`, which is byte-for-byte the
  old free `with_state_path_access` (record_read, `state`-ancestor lookup, derived root) with the
  lock decision moved into `publication_access`. For `Access::Lock` the behaviour is identical to
  base; for `Access::Held` every one of the 26 exposed guarded methods was traced: each either
  enters through `with_repository_read` (`manifest`, `closed_manifest_scope`, `list_scope_directories`,
  `list_contributions_after_direct_read`, `list_synthesis_packets`, `project_proposal_cards`,
  `list_proposal_definitions`, `list_dispositions`, `list_assertion_records`,
  `validate_ideation_scope{,_with_actor_ids}`) or through `state_path_access` (every shard family,
  messages) — all resolve to `operation()` under `Held`. Nested plain reads still re-enter via the
  thread-local `HELD_LOCKS` (`publication.rs:60`) exactly as at base, so no path takes a lock twice.
- **`plan_typed_spec` is genuinely read-only in Plan mode**: all mutations (`replace_records` ×4,
  `raise_requirement_reviews`, statement writability) sit behind
  `matches!(mode, ReconcileMode::Apply)` (`typed_specs.rs:215`); `implementation_bindings::reconcile`
  mutates only in-memory vectors. Not exposed on `GuardedStore` (see Minor 1).
- **Manifest and scope-directory reads** route through `with_repository_read` on `self.layout` —
  identical to base for plain stores; lock-free under `Held`; all shard paths sit under
  `<root>/.provenance/state/…` so the `state_path_access` ancestor search always matches.
- **The guard carries its own layout.** `PublicationGuard.layout` is private, set at both
  construction sites (real lock and read-only validation), read only through the `pub(crate)`
  `layout()` choke point that both `StateStore::under_guard` and `snapshot_state_under_guard(guard)`
  consume; the free two-argument forms are gone and both compile-fail cases
  (`guarded_store_wrong_repository`, `snapshot_wrong_repository`) pin E0061.
- **No write can escape the read-only type.** `GuardedStore` has no `Deref`/`Clone`/`AsRef`/`From`,
  its `store` field is visible only to `access::{,guarded_readers,tests}`, all of which call reads
  only; `mutate_jsonl_records` (`publication.rs:438-450`) always takes
  `with_repository_publication`, and every writer entry point wraps in it (or
  `with_lifecycle_lock`), so even a hypothetically reachable `Held` store would lock rather than
  deadlock on write.
- **Snapshot copy retained, catch-up/rebuild unchanged**: `catch_up.rs:68-69` and `materialize.rs:50-51`
  still `snapshot_state_under_guard(guard)` + `StateStore::new(snapshot.layout())`; all snapshot
  machinery (`StateSnapshot`, `snapshot_state`, `snapshot_state_unlocked`, `copy_tree`) intact.
- **No scope creep**: no `VALIDATION_VERSION`, no `read.*` settings file (`provenance-sdk/src/settings.rs`
  is pre-existing SDK settings, present at base), no `refuse_stale` implementation beyond the
  pre-existing reserved `ReadRefusal::RefuseStaleUnimplemented` (present at base, reader.rs:56),
  no in-place hashing.
- **Rule records**: both ids under 55 characters (39 and 43); each one atomic behavioural obligation
  under the real parent `req_query_answers_carry_a_freshness_stamp` (present in
  `requirements/req.jsonl`); each has exactly one `#[rule]` on a genuine single choke point
