## Minors

1. **The body's "the one comparison against canonical bytes over a store of real
   size" is not literally true — and the truth is stronger than claimed.**
   `every_stored_row_of_the_repository_state_reads_back_as_written`
   (`crates/provenance-store/src/operations/queries/tests/tables.rs:139`, on `main`
   since the W3 flips, untouched by this PR) already reads back **every** canonical
   row of the eight kind tables over the same `repository_state` copy and compares
   each column value against the canonical record (`assert_rows_read_as_written`,
   tables.rs:101-131). The plan's F.2 sentence ("it is the one comparison to
   canonical bytes over a store of real size after the baselines go") and the PR
   body's repetition of it should not be read as an inventory: there are two
   comparisons over the repository's own state, and they catch different faults.
   The count test's distinctive contributions are (a) the three integration tables,
   which `tables.rs` does not cover, and (b) the **extra-rows direction**, which
   `fetch_one`-by-id cannot see (mutation R6 below failed the count test while
   the per-row test alone would have passed it). Neither test compares raw bytes —
   both compare against canonical *reads* (`list_*`). Practical consequence: nobody
   should later delete the `tables.rs` read-back believing the count test
   supersedes it. Reproduction: see Reproductions R5/R6.

2. **A value-corrupting fault on the three integration tables is invisible to every
   remaining guard.** The count test catches row-count drift on
   `implementation_bindings`, `verification_bindings`, and `requirement_reviews`,
   and `tables.rs` reads back only the eight kind tables — so a projection that
   wrote a binding row with one wrong column value (same count, same id) passes
   both, where the same fault on a kind table is caught by `tables.rs`. This is
   consistent with the plan, which names a count invariant for these tables and
   nothing stronger; noted so the residual gap is on record while the baseline that
   used to cover it is being deleted. Not blocking: bindings feed `resolve_symbol`
   and the stamps, whose pinned answers still hold.

## Nits

1. `search_answers_new_kinds_after_every_settled_kind` (tests.rs:198) names more
   than its store can show: `seeded_store` holds exactly one settled kind
   (requirement) plus the two appended kinds, so the served assertion proves
   "after a settled kind". This is exactly the strength of the deleted
   `load_orders_new_kinds_after_every_settled_kind` (same store, same expected
   order — the deleted test asserted the same three-element order), and the full
   rank table is pinned unit-level by
   `rank_appends_the_new_kinds_after_the_six_settled_positions` (tests.rs:178), so
   there is no coverage regression. Name-only.
2. `every_operation_answers_over_the_repository_state` (comparison.rs:155-163)
   returns early, printing a skip line, when git is not on the path — the whole
   test then verifies nothing while reporting pass. This cannot silently happen in
   an environment where the rest of the suite runs (the pinned answers test
   `expect`s the git-derived base commit and would fail loudly), so it is a trap
   only for filtered single-test runs.
3. The plan's K.4 step list includes "docs/release.md gains the command, the
   checklist line, and the criterion"; those landed in the merged PR 205 rather
   than this PR. The tree satisfies the requirement either way (docs/release.md:54-105
   carries the command, the checklist line, the criterion, and even the "24 cases"
   get reference and the "timing rows for all eight operations" expectation), so
   nothing is missing — the departure is only in which PR carried it.

**Would the count test catch drops and duplications?** Yes, in both count
directions (R5: minus one row → red; R6: plus one row → red). What it cannot catch
is count-preserving corruption, and only on the integration tables is there no
second guard (Minor 2). The per-row guard for the kind tables is `tables.rs`
(Minor 1).

**`comparison/requests.rs::for_store` sampling.** The deleted version sampled
through `records::load` (whole graph, rank-then-id order, first `PER_KIND`=3 per
kind, `include_retired=true`). The replacement runs one served search per kind with
a per-kind needle, `include_retired = true`, `limit = PER_KIND`; the served search
answers each kind `ORDER BY id` (`cache/read/records.rs:160`), so the sample is
again the first three records per kind in id order, retired included — **same
breadth, same order, same record set**. Measured over the repository's own state
(R4): all eight kinds sample exactly 3 each; the request set holds 24 `get`
(matching docs/release.md's "`get` served summary (24 cases)"), 24 `impact`, 25
`neighbors`, 25 `trace`, 3 `evidence` (+3 with a base commit when one is bound),
4 `search`, 1 `resolve_symbol`, plus `stale` when a base commit exists — the same
request shapes as before, with only the sampler swapped. The per-kind needles
(source, req, res, rule, top, q, domain, boundary) match every id prefix in this
repository's shards (checked shard by shard), and `searchable_text` always
includes the id (`provenance-core/src/protocol/node.rs:76`), so a broken search
degrades the sample rather than silently emptying it — and a fully broken search
fails the every-operation test (R3).
