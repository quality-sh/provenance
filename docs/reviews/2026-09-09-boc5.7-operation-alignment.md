## Generated transport coverage versus native engine capability

The generated surface is complete for what it exposes:
`packages/provenance/src/generated/client.ts` carries one method per catalog
entry (30 operations, `PROTOCOL_VERSION = 7`), each call body carries
`context` (`repository`, `scope`, and `freshness` on the eight structured
reads — `contracts/operations/openapi.json`,
`GetRequestInputRepositoryContext`), and mutation paths map lost or
undecodable responses to `UncertainWriteError`
(`generated/runtime.ts`, `UncertainWriteError` class; per-operation mapping in
`client.ts`). Transport is not the constraint anywhere below.

Where a capability is missing, the constraint is the catalog and, in three
cases, the native writer itself:

1. Bulk scope reads: `StateStore::list_requirements`, `list_resolutions`,
   `list_rules`, `list_sources`, `list_topics`, `list_questions` exist
   (`crates/provenance-store/src/state_store.rs:164-185`) and return complete
   arrays, but the catalog (`operations/catalog/entry.rs:78-110`) exposes
   list operations only for threads, messages, and the proposal family.
2. Thread addressing and thread status: `StateStore` has no writer that sets
   `ThreadStatus` at all (`state_store/thread_writers.rs` contains only
   `post_thread_message`), so there is nothing to expose.
3. Record status and severity updates: no native writer changes a
   Requirement, Resolution, or Rule status or a Rule severity after creation
   (creation inputs carry them; `update_question` is native-only and covers
   Questions only).

## The two scenarios, answered

- A fixture method with no exposed operation: `setThreadStatus` (B12) is the
  exact case — no native writer and no operation exist; the fixture simulates
  persistence in the browser. `setRecordStatus`/`setRuleSeverity` (B7, B8)
  have no native writer either. `getRecords` (A1) and `fog` editing (B2) are
  the contrast case: native capability exists, only the catalog entry is
  missing. Each row names the owning bead.
- A document requiring more than 200 records: every paginated read caps at
  `QUERY_MAX_LIMIT = 200` with `has_more` and no cursor (A2), so no sequence
  of generated calls can prove completeness for the builder's fixed-point
  scan. The report does not accept a truncated `neighbors`/`search` result as
  the document. The gap closes with the bulk scope read in A1.
