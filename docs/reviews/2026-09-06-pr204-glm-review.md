## Verdict

**Needs fixes — small ones.** The stage delivers what section C and the K.1b paragraph require: the pass hashes in place under the guard, retries unstable units three times, refuses with `catch_up_failed` at the stored serial, validates changed scopes and every scope after a global change, rebuilds in place, deletes the snapshot machinery, and adds `VALIDATION_VERSION` with migration 023 and the `ensure_current_schema` refusal. Every gate I could run reproduces: fmt, clippy `-D warnings`, the full Rust workspace suite, the TypeScript suite (86/86 runtime, types, packed), byte identity over the repository's own state and over identical state copies, and the coverage scan naming none of the four new rules. All eleven quoted RED messages appear as observed failures on `f126ea8` (R2); the two refusal-preserving tests pass there, exactly as the body says.

The blocking item is one honesty gap in the new mechanism, demonstrated with a failing test: the hash, parse, hash-again check accepts an edit that is reverted inside the window, so the projection can commit rows under a digest that describes bytes those rows never came from — permanently, because the next pass sees no change. The mechanism is exactly what C.2.4 specifies, so this is not a departure; but the rule record and `docs/cache.md` state the resulting invariant more strongly than the code provides, and the demonstrated case contradicts them. The fix is a disclosure sentence and reconciled rule wording, not a redesign. The five disclosed departures are judged below; four are sound and one is incomplete.

## Majors

### M1. An edit reverted between the parse and the second hash is accepted, and the projection then serves rows its stored digest does not describe — the rule statement and docs over-claim

`stable` (`crates/provenance-store/src/cache/materialize/validation.rs:109`) accepts a parse when the hash after the parse equals the hash before it. That does not establish that the parsed bytes were the hashed bytes. If an unlocked editor moves the bytes from A to B after the first hash, the parse reads B, and the editor restores A before the verification hash, the two hashes match, the parse of B is used, and D(A) is stored. The committed rows then describe B while every digest row attests A. The next pass hashes A, finds it unchanged, and serves the B-derived rows for ever; nothing heals until A changes again. The base implementation could not do this: the digest was computed over the copy the rows were loaded from, so a stored projection was always internally consistent.

Reproduced (see Reproductions R1): with one temporary probe between `parse()` and the verification hash, the pass commits `statement = "Second edit"` under a unit digest equal to the digest of the on-disk `"First edit"` bytes, and a second pass serves `"Second edit"` at the stored serial with no revision. The one-line probe is the only thing a stock test cannot do today; there is no probe point between the parse end and the verification hash.

Why this is Major and not a design rejection: C.2.4 specifies exactly this check, three attempts, and the unlocked-editor trust model, so the code implements the approved plan faithfully, and the plan's threat statement ("only an unlocked editor can do" it) still holds. What is wrong is the contract surface the PR itself writes: `rule_catch_up_stores_the_digest_of_parsed_bytes` states "Catch-up stores the digest of the bytes it parsed", which the demonstrated case falsifies, and `docs/cache.md` says "If the two hashes match, the pass can use the parsed records and their digest" without naming the residual. Two adjacent residuals share the same root and deserve the same sentence: (a) the scope validators that run inside `UnitReader::global`'s retry closure read scope shards that the global unit's verification hash does not cover, so a torn read during a changed-global validation can render a verdict the settled bytes would not; (b) the rebuild stores the global digest taken at pass start, so a mid-rebuild dictionary edit is attested by the old digest until the next pass re-derives it.

Required fix (small): one sentence in `docs/cache.md` ("a revert inside the hash, parse, hash-again window is accepted; the stored digest then describes the bytes at hash time, not the parsed bytes") and a matching sentence in the rule's `description` (or a reworded `statement` such as "Catch-up commits only parses whose unit hashes before and after match"). Nothing else in the stage depends on the stronger claim.

### Judging the author's disclosed departures

- **Parsed records held in memory until the second hash matches.** Sound and necessary: the loaders take bytes, not the store, so a discarded retry cannot write rows. `ScopeRecords` and `FamilyRecords` are plain data; nothing escapes the retry loop. Accepted.
- **Scope discovery from manifest bytes retained during hashing.** Sound: in the unchanged-global path the manifest parsed is byte-for-byte the hashed bytes (and `manifest_from_bytes` keeps the schema-version check); in the changed-global path the manifest is re-read through the store and the verification hash covers it. The two review-fix tests cover both. Accepted.
- **`units_hashed` counts scanned units and excludes verification hashes.** Matches the previous observable count (one hash per unit per pass); existing tests keep their expectations. Accepted — but see Nit N1 for the rebuild report.
- **Eighteen families where C.2.4 says nineteen.** Correct; `ProjectionFamily::ALL` has 18 members and the stage adds none. The plan text is wrong and the PR body says so. Accepted.
- **Unsupported-entry refusal moved from the copy step to the hashing step.** True for hashed units, but incomplete: the refusal's coverage narrowed. See Minor m2.

## Minors

### m1. A rebuild validates every scope twice; a changed global validates changed scopes twice

`UnitReader::global(None)` (rebuild) and every changed-global catch-up pass take the slow path, whose parse validates every scope; then `UnitReader::scope` validates the same scope again inside its own retry loop. A rebuild with N scopes runs the validators 2N times where the old code ran them N times, and the rebuild is the first-read path C.1 timed at ~144 ms. Correctness is unaffected and the ordering (ideation then graph, manifest order) is unchanged, but the redundancy defeats part of the point of item 2 on the rebuild path. A `validate` flag through to `scope()`, or skipping the per-scope validation when the global step just validated that scope, would halve it.

### m2. The unsupported-entry refusal now covers only hashed units; an unsupported entry in a departed scope directory is silently ignored

The deleted `copy_tree` refused a symlink or special file anywhere under `state/`, including directories the manifest no longer names. The hash walk visits only the global unit and each manifest scope, so a symlink inside `state/scopes/<departed>/` is never seen. Reproduced (R3): base refuses with `unsupported state entry: .../state/scopes/second/external-link`; head accepts the pass and commits serial 2. The author's disclosure says the refusal moved from the copy step to the hashing step, which is accurate for hashed units but omits the narrowed coverage. Severity is low (a symlink in dead state now bricks nothing instead of bricking every read), but it is a behaviour change versus base that neither `docs/cache.md` nor the PR body states.

### m3. `ensure_current_schema` and `version_changed` disagree on a stored version greater than the constant

`version_changed` routes catch-up to a rebuild on `version != VALIDATION_VERSION` (both directions), while `ensure_current_schema` refuses only `version < VALIDATION_VERSION`. After a downgrade, `annotate_only` answers a projection a newer validator built as current, while a `catch_up` read on the same file tears it down and rebuilds it at the older version. Both readings are defensible from the plan's own words ("refuses a stored validation version behind" versus "whose stored version differs"), but the two policies answering differently about the same file is an accident of wording rather than a decision. Either refuse on `!=` in `ensure_current_schema` too, or record the downgrade stance in the rule description.

### m4. The coverage gate's absolute count does not reproduce

The PR's gate table says 85 warnings. I measure 81 with the head binary and 81 with the merge-base binary over the identical tree (identical warning sets, verified set-equal). The substantive claims hold — the four K.1b rules are named by no warning, and the two binaries' reports match — but the number 85 did not reproduce on any checkout I could build (750 files scanned, `commit b19e487` resolved). The scan's warning set is also environment-dependent in a way worth knowing: over a linked git worktree whose `--path` cannot resolve the repository root, the same binaries report 35 warnings with rule validation skipped (`commit: null`). The gate table should either quote the reproducible number or state the checkout it was taken on.

## Nits

- **N1.** `CatchUpReport.units_hashed` is 0 on every rebuild report while the new doc comment says "Units scanned. Verification hashes do not add units." — a rebuild scans every unit. The value is pre-existing; the comment is new, so the PR documents the field into a contradiction with its own rebuild path. Set it or reword the comment.
- **N2.** `a_unit_with_a_symbolic_link_is_refused_before_parsing` and `a_validation_version_move_refuses_an_unchanged_invalid_scope` carry no `#[verifies]`. They are good tests (both RED on base); binding them to `rule_catch_up_hashes_canonical_state_in_place` and `rule_validation_version_move_rebuilds_the_projection` respectively would make the four rules' evidence complete.
- **N3.** `docs/cache.md` states "The pass lists scopes from the exact manifest bytes used in the global hash." That is literally true only for the unchanged-global path; the changed path re-reads the manifest through the store and leans on the retry check. The PR body words it correctly ("Changed globals still use the retry check"); the doc could carry the same qualifier.
- **N4.** Under `annotate_only`, a database that has migrations but no `projection_validation` row (initialised, never materialised) now refuses where base answered. Plan-conformant (a missing version is behind), self-healing on the first catch-up read, and unreachable from the CLI today, but it is a new refusal in the init window worth a line in the release notes.

## Things checked and found fine

- **Guard held across the whole pass.** `catch_up_state`, `freshness::catch_up`, and `materialize_state` each hold the guard from before the pool open through the commit; the existing probes assert the lock is held at migrations and at `materialize_before_commit`/`catch_up_before_commit`, and those tests pass.
- **No second lock inside the pass.** Every canonical read in catch-up and rebuild goes through `GuardedStore<'g>` (`Access::Held`): the unit reader, the validators, all 18 family readers (including the newly added `list_requirement_reviews`), and `relation_rows::scope_rows`. `family_rows`/`collaboration_records`/`record_rows` now take bytes, not the store. No `StateStore::new` is reachable inside the pass; the compile-fail cases (`forged_guard`, `guarded_store_outlives_guard`, `guarded_store_write`, `guarded_store_wrong_repository`, `read_after_stamp`) and the `under_guard` doctest still gate the constructor. Deleting `snapshot_wrong_repository` is sound: `under_guard` takes only the guard, so a foreign layout is no longer expressible.
- **Exhausted retries.** Three unstable attempts bail with `canonical state changed during catch-up under <unit>`; the read answers at the stored serial with policy `catch_up_failed`, byte-identical result, serial, and digest (`a_retry_that_runs_out_answers_catch_up_failed`, RED on base, green at head). A parse error with stable hashes surfaces immediately without wasted retries; a parse error during instability is retried (`a_manifest_repaired_after_hashing_is_retried`).
- **Manifest race.** Unchanged globals parse the exact retained hashed bytes (schema-version check included); changed globals re-read through the store under the retry check. Both review-fix tests are RED on base and green at head.
- **Validation skipping.** An unchanged invalid scope is served (accepted per L.5, `materialize` still refuses — `an_unchanged_invalid_scope_does_not_refuse_a_read`); a changed scope is validated alone; a manifest byte change (even one that parses identically) validates every scope and commits nothing on refusal (`a_manifest_change_validates_every_scope`); a validation-version move routes to a full rebuild that restores deleted rows (`a_validation_version_move_routes_catch_up_to_a_full_rebuild`) and refuses an unchanged invalid scope, committing nothing and leaving the stored version (`a_validation_version_move_refuses_an_unchanged_invalid_scope`). `ensure_current_schema` checks the migration gate before the version gate, so a pre-023 database refuses on migrations with the right error; `annotate_only` refuses a rewound version (`annotate_only_refuses_a_projection_from_an_older_validator`, RED on base, green at head).
- **Migration 023 and the rebuild transaction.** `clear_cache` now also clears both digest tables inside the rebuild transaction, and `write_stamp` writes the revision, validation version, and instance id in that transaction; the digest rows are built from the parsed bytes via the unchanged `revision_digest_from_stored_rows` recipe, and the upgrade comparison shows the digest is identical to the base recipe's.
- **Unsupported-entry refusal for hashed units.** Symlinked scope roots, symlinked intermediates, and symlink/special entries inside hashed directories are refused at the hash step (`a_unit_with_a_symbolic_link_is_refused_before_parsing`, RED on base — base silently skipped them in `collect`, the copy was the refusing step); the narrowed unlisted-directory case is m2.
- **Rules.** Four records, ids 45/47/42/52 characters, all under `req_query_answers_carry_a_freshness_stamp` (exists), all active with atomic behavioural statements; each has exactly one `#[rule]` site (`UnitReader::new`, `UnitReader::global`, `stable`, `version_changed` — the right primary implementations) and `#[verifies]` evidence whose RED behaviour was verified in R2. `coverage scan --validate-rules` names none of them and the base/head warning sets are identical. CONTEXT.md's "Validation version" entry is plain-worded.
- **No scope creep.** No settings file loading, no `--freshness` flag, no `ReadRefusal::Stale`/`UnitUnreadable`, no baseline or pinned-answer deletions, `READ_DERIVATION` still 1, `read_policy.rs` untouched; the only deletions are the snapshot machinery, its two compile-fail proofs (folded into the constructor proof), and one duplicate copy doctest.
- **Test bookkeeping.** 379 → 390 (+14, −3, one ignored) verified by direct count on both trees; the named removed tests are all present in the base tree and gone at head.
