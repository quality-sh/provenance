## Findings (most severe first)

**F1 (medium, latent). The compile-time guard is bypassed by type aliases, newtypes, and wrappers — the primary guarantee is overstated.**
`crates/provenance-macros/src/relations.rs:205-225`: `shape_of`/`is_stable_id` recognize only the literal spelling `StableId` (bare, `Option<StableId>`, `Vec<StableId>`) or an `Option`/`Vec` of a struct with `via`. Any other spelling falls to `Shape::Other`, and `expand` (relations.rs:69-80) silently `continue`s over a field with no attribute when the shape is `Other`. Proven by compile probe: a struct with `type RequirementId = StableId; pub parent: RequirementId`, one with `pub parent: Box<StableId>`, and one with a bare nested struct field all compiled through `#[derive(Relations)]` with `RELATIONS` empty and no diagnostic — the guard that `crates/provenance-core/src/model/relations/decl.rs:3-5` and `model/relations.rs:6-8` promise ("a reference field without a declaration cannot exist: the derive refuses it at compile time") does not hold for these spellings. The backstop (`relation_walk.rs` serde walk) covers only the seven kinds, collects only keys ending `_id`/`_ids` plus declared names (`relation_walk.rs:33-50`), and collects them into a `BTreeSet`, so two fields serializing the same key collapse and a reference field named `parent` or `successor` with an alias type escapes it too. Failure scenario: someone adds `pub successor: RequirementId` to `Requirement` next quarter; it compiles with no `#[relation]`, gets no validation, no dangling check, no walk row, no projection row, and no refusal anywhere — silently unmanaged. No current field is affected (all seven kinds spell `StableId` literally); fix is to refuse any unrecognized `Shape::Other` field without `#[relation(none)]`, or to type-check against the resolved `StableId` path.

**F2 (medium). State-level cycle validation covers requirement kinds only; resolution/source supersession cycles enter canonical state unrefused, and two of three chain relations are untested.**
`crates/provenance-store/src/state_store/graph_validation.rs:17,31,49-56`: `REQUIREMENT_CHAINS = ["refines", "depends_on", "supersedes"]` is walked over `list_requirements` only. `Resolution.supersedes` and `Source.supersedes` also carry to their own kind (section C), but no validator pass ever walks them. Proven empirically: planted `res_one.supersedes = [res_two]` and `res_two.supersedes = [res_one]` in a scratch repository — `provenance check` exits 0 and `provenance materialize` succeeds. The write path refuses this (`reference_writers.rs:116-123,159-166` guard any relation whose target is the owner's kind), so only a merge, an import, or a hand edit can introduce it — but the merge gate runs per-record checks only by its own design (`merge/validation.rs:8-13`), and `import.rs:229` runs `validate_repository`, which inherits the same hole. Compounding it, my mutation run: deleting `"depends_on"` and `"supersedes"` from `REQUIREMENT_CHAINS` leaves all four tests in `state_store/tests/graph_validation.rs` green — only `refines` is pinned. Plan section E promises the validator refuses "a `refines`/`depends_on`/`supersedes` cycle in state"; the implementation quietly narrows that to one kind, and the narrowing is undeclared. Failure scenario: a merge between two branches that each added `supersedes` entries lands a mutual supersession; `check`, `materialize`, and `export` all accept it; the wiki renders both records as superseding each other while the gap policy reports nothing.

**F3 (low, latent). The create writers' required check is hand-coded, so the declaration does not drive it.**
`crates/provenance-store/src/state_store/rule_writers.rs:32-33` hardcodes `!requirement_ids.is_empty()` → "a resolution needs one requirement"; `:103` hardcodes the same for rules. The add/clear writers (`reference_writers.rs`) read `decl.required` from the table; the create writers do not. The PR's own mutation table concedes it ("the create writer's own check stays green" when `Rule.requirement_ids` is made optional). The binding resolution demands "One declaration per record kind names its reference fields, and the writers, the validator, the gap policy, and the projection derive from it", and plan section E says requiredness "is enforced from the table by the writer". Today the duplication is consistent (the strings match `required_refusal`), but a future required relation, or a requiredness change, is enforced everywhere except at create. The PR declares neither this nor the two-message split it creates.

**F4 (low, standards). One net-new `#[allow]` suppression on a touched file.**
`crates/provenance-cli/src/cli/policy.rs:8,70` carry `#[allow(clippy::large_enum_variant)]`; be9b52c had one in that file (and one in `cli/knowledge.rs:55`, which moved to `:8`). The second `policy.rs` attribute is new: the command enum grew (the new reference subcommands) and the response was to silence the layout lint instead of boxing the large variant. Everything else is clean: no Rust file over 500 lines anywhere in the repo (checked repo-wide, not just touched files), no TODO/FIXME/review residue added, the deslop pass holds (`edge` survives only in `lineage_validation.rs`'s graph-theory sense, the frozen migration filename `002_sources_requirements_edges.sql`, and `domain_knowledge` substrings), and the version-literal discipline holds in production code (the `"const": 1` hits in `handlers/schema/artifacts/contribution.rs` et al. are the untouched pre-cut ideation-artifact contracts, out of this PR's scope).
