## Proposed end state and module seams

One canonical read operation returns an addressed Discussion page for a scope or one parent. It checks the selected grant set and optional parent before querying. The SQL selection applies scope, permitted parent kinds, optional parent, and status before taking `limit + 1`. A returned entry has the actual Discussion ID, parent, status, and a bounded excerpt of the opening Message. The cursor includes every selector and uses the shared revision check. No count or cursor can reveal rows outside the permitted selection. An unchanged revision yields each selected Discussion once.

One addressed conversation operation returns the current journal head and the first or next bounded Message page from the **same `ReadSnapshot`**. An absent or denied target has the existing explicit read refusal. A continuation names the Discussion and pinned selection; it cannot change parent, scope, or revision. The existing exact parent read and message reader remain available to nested consumers.

One canonical target-addressed write path resolves a parent for Start or the journal head for Reply **inside** repository publication. It then calls the existing `WriteDiscussion` flow and returns its receipt. It preserves request ID and intent digest replay, expected-version checks, parent and owner checks, canonical Thread membership, and resolved/closed behavior. Refusals for stale version, wrong membership, closed container, resolved reply, changed intent, and missing or unsupported targets are typed before they enter CLI or MCP.

The external seam for human actions belongs in `provenance-porcelain`. Its interface contains typed semantic request/result forms, validation, and one readable renderer for CLI and MCP. Catalog operations remain the source of canonical reads, writes, schema, and failure data. CLI and MCP adapters parse syntax, apply transport admission, invoke the shared porcelain behavior, and package JSON or MCP structured data. CLI uses its local in-process host; it does not start an HTTP server. These are proposed module responsibilities, not mandatory symbol names.

## Behavioral examples for implementation review

1. In one scope, `req_a` has Discussion `d1` active and `d2` resolved. Scope and `req_a` lists return `d1` by default. `--status resolved` returns `d2`; `all` returns each once, with its true parent and opening excerpt. A page limit of one returns the next selected Discussion, not an unfiltered row or a legacy group with invented fields.
2. A grant that permits Requirement discussions but denies Source discussions returns no Source row, count, or continuation in a scope list. A direct request for a denied parent or Discussion refuses without exposing its content. A cursor for `active` cannot be reused for `all`; a changed projection revision refuses continuation.
3. A conversation request for `d1` returns its current version and ordered first Message page. A write that commits while the read runs cannot make the returned head newer than its returned Messages. The next page retains the same Discussion selector and revision.
4. Two Starts on `req_a` produce separate Discussion IDs, root Messages, and statuses. A Reply addressed to `d1` changes only `d1`. One expected-version race has one success. Repeating the same request ID and intent after restart returns the original receipt; reusing that ID for another body refuses without another Message.
5. Existing nested `discussion-containers` and legacy-message routes remain readable. A legacy group has a Thread ID and container status; it gets no Discussion ID or Discussion status.

The new open `topic_sc2t_discussion_identity_routing` and `question_sc2t_discussion_get_collision` ask Ben how default get handles a string that identifies both a graph record and a Discussion in one scope. Review options include an explicit kind selector, a typed ambiguous-ID refusal, or a documented precedence rule. Each affects default-get behavior and its tests. The plan selects none. It does not reserve new ID prefixes, change uniqueness, or alter stored records. The choice gates only the colliding-ID default-get path in PR 3.

## Verification for the future runtime PRs

**Automated:** Each PR runs focused Store, porcelain, CLI, and in-memory MCP tests for the cases above. Verify catalog request/result schemas against the typed operations, and run `provenance coverage scan --path . --scope default --validate-rules` to show binding and verification gaps honestly. On a maintainer host, stage new files before CI snapshot checks and use `env -u PROVENANCE_CI_LOCAL python3 scripts/agent-bin/cargo test ...` or the equivalent permitted CI shim. Keep all Rust files, including tests, under 500 lines. No native Cargo, rustc, formatter, codegen, or npm build runs on mint.

**Manual:** Review a scope list and an addressed conversation in readable CLI and MCP content. Compare each with its JSON or structured result for IDs, status, version, cursor, and truncation. Review denial and collision results without relying on string parsing in an adapter. Check that CLI execution stays in-process. These checks are review guidance; this planning PR does not perform runtime implementation or claim a fresh runtime pass.
